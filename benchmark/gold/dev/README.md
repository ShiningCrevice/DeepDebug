# 人工参考状态与报告（仅开发/评测使用）

`dep_001.json`、`dep_002.json`、`path_001.json`、`shape_001.json`、`device_001.json` 与 `oom_001.json` 是人工填写的 `DiagnosisState`，包含登记材料、参考证据、假设和报告；不是 Agent 运行轨迹。所有参考状态的工具历史为空、预算用量为零，修复验证为“未执行”。失败输入的采集不能当成修复后的成功验证。

| 案例 | 参考首选原因 | 应使用的额外证据 |
|---|---|---|
| dep_001 | 预期和实际解释器相同，目标环境未发现 pydantic 元数据且导入失败 | 目标快照、预期解释器配置与日志解释器 |
| dep_002 | 项目环境存在依赖，但任务用了另一个空环境解释器 | 两个不同环境快照、预期解释器配置与日志解释器 |
| path_001 | 从 project/jobs 解析相对路径，目标文件实际在 project/checkpoints | 日志工作目录、源码、配置、采集时的文件布局与目标快照 |
| shape_001 | 输入末维 5 与 Linear 的 in_features=4 不一致 | 日志形状、配置、前向代码及快照 |
| device_001 | 模型在 CUDA、输入保留在 CPU | 日志中的实际设备、迁移代码、配置及快照 |
| oom_001 | 64 MiB 申请超过进程显存配额 | 日志配额/申请量、配额设置代码、配置及快照 |

两例均采用“有支持但待验证”，不将分发包元数据存在当成导入一定成功的证明。快照在独立进程中采集，也不代表训练进程的完整状态。两个案例仅覆盖 Python 依赖问题，不能计为 PyTorch/GPU 训练验证。

`dep_002.md` 是同一参考报告的人工可读版本。测试读取这些文件验证协议和引用；未来运行时只可登记 `benchmark/dev/*/materials/` 下的材料，禁止把 gold 或本文件送给 Agent。

路径案例的 `layout.json` 描述采集时临时环境中的事实；不能用仓库材料目录下的文件状态替代。参考报告的建议路径尚未执行验证。

OOM 参考原因限定为进程分配器配额，不能把日志中的通用碎片化建议当成实例证据；未执行配额调整或修复验证。设备和 OOM 日志来自真实 CUDA 进程，环境快照在独立进程采集。
